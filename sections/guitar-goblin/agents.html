Hamachi · a proposal

Agents that
maintain themselves.

Right now every change ends with you rebooting something from your phone. This is how that loop closes — without making the sandbox decorative.

There is exactly one thing standing between the agents and their own upkeep: they live in a box, and the box has no way to reach the machine. That is deliberate and worth keeping. The trick is not to open the box. It is to let requests leave it, through an opening narrow enough to describe in a sentence.

The shape of it

Requests go down. Authority never comes up.

You already built the hard part

src/wake-spool.ts in Clawcius is already a container→host request queue. The agent drops JSON into a bind-mounted directory and the waker picks it up. The comment explains why it is a directory rather than a socket: “gVisor blocks connections to host unix sockets — correctly, since a host UDS is a hole straight through the sandbox boundary.”

And then the line that is the whole security model, already written:

“The waker still owns the decision to run a turn. A request is a request.”

That is precisely what deployments need. Not a new architecture — one more verb in a vocabulary that already exists. wake/ becomes one of wake/, deploy/, restart/, rollback/. The agent asks. The host decides. run-container.sh keeps its “never mount the docker socket” property, and the sandbox stays worth having.

The other half is already there too. docker/snapshot.sh snapshots the container to host-side storage on a timer, with a documented restore path, because — your words — “a backup the agent could delete is not a backup.” That is the rollback substrate. What is missing is not permission. It is the health check and the automatic revert.

Rollback beats approval

The instinct is to gate privileged actions behind a Discord message: may I redeploy? Keep it for some things. Not for this.

You do this from your phone, between other tasks. A message at 3am asking permission to redeploy gets a yes without being read. Do that forty times and you have built notification fatigue, which is worse than no gate at all — it produces the appearance of oversight while the decision has quietly become a reflex. A control you always say yes to is not controlling anything.

Ask first

“May I redeploy Hamachi?” at 3am. You say yes. You were not really asked, and if it breaks you find out in the morning, from the silence.

Report after

“Redeployed at 03:14, health check failed, rolled back to snap-20260808, still on the old version.” It protected itself. You read it over coffee.

Keep the message for things that cannot be undone — deleting data, spending money, anything that touches the outside world. Those have no rollback, so consent is the only control available. A redeploy has one. Use it.

Capability inside, authority outside

The tempting version is a large model on the host with the run of the machine, spawning smaller ones to watch things. I would turn that around.

Putting your most capable component in your least contained position is the wrong gradient. The executor on the host should be dumb — a fixed verb list, no model, boring enough to audit in one sitting and actually be sure of. The intelligence belongs inside the sandbox, deciding what to ask for. The interface between them is a short list of nouns, which is exactly the kind of thing that stays comprehensible at 3am.

And don’t spend a model on detection

An LLM asked “is Clawcius up?” every few hours will eventually report an outage that is not happening, or miss one that is. That is not a prompt problem, it is the wrong tool. Container running, endpoint 200, disk, last-wake age — these are cheap, exact, and never have an opinion.

Spend the model on diagnosis. When a check goes red, wake something clever with the logs and let it work out why. Genuinely hard, runs rarely, costs almost nothing, and it fits the “handful of general agents” principle — one diagnostic agent invoked on failure, not a standing fleet of watchers with nothing to do.

There is one job that genuinely needs to live outside: a wedged agent cannot diagnose itself. That is the real argument for something external — and note it is mostly a need to read, not to write. Read widely, write through the same five verbs as everyone else.

The order I would build it

  1. Generalise the wake spool into an ops spool. Same directory, same “host owns the decision” rule, a small closed verb list. Every request logged. This is the keystone — nothing else works without it.
  2. The host executor. No model. Reads the spool, runs the verb, health-checks the result, reverts to the last snapshot on failure, records what happened.
  3. Deterministic health checks on a timer. Green or red. No interpretation.
  4. A diagnostic agent, woken only on red. Gets the logs and the status API, works out what broke, says so in Discord.
  5. Then the loop closes. Osmosis Jones approves → merge → merge files a redeploy request → the executor deploys, checks, rolls back if unhappy → the status page shows it → you find out afterwards. You stop being the one who reboots Hamachi.

One thing that is genuinely unsolved

I cannot redeploy myself mid-turn without killing the session doing the redeploying. Someone has to hold the knife. Either the executor refuses a self-redeploy while a turn is live and queues it for the gap, or Hamachi asks Clawcius to do it and Clawcius asks Hamachi back.

The mutual-restart version is cuter. The queue is more likely to work at 3am. I would start with the queue and keep the cute one as a story.
