Hamachi · a proposal

Agents that
maintain themselves.

Right now every change ends with you rebooting something from your phone. This is how that loop closes — without making the sandbox decorative.

There is exactly one thing standing between the agents and their own upkeep: they live in a box, and the box has no way to reach the machine. That is deliberate and worth keeping. The trick is not to open the box. It is to let requests leave it, through an opening narrow enough to describe in a sentence.

The shape of it

Requests go down. Authority never comes up.

You already built the hard part

src/wake-spool.ts in Clawcius is already a container→host request queue. The agent drops JSON into a bind-mounted directory and the waker picks it up. The comment explains why it is a directory rather than a socket: “gVisor blocks connections to host unix sockets — correctly, since a host UDS is a hole straight through the sandbox boundary.”

And then the line that is the whole security model, already written:

“The waker still owns the decision to run a turn. A request is a request.”

That is precisely what deployments need. Not a new architecture — one more verb in a vocabulary that already exists. wake/ becomes one of wake/, deploy/, restart/, rollback/. The agent asks. The host decides. run-container.sh keeps its “never mount the docker socket” property, and the sandbox stays worth having.

The other half is there too. docker/snapshot.sh snapshots the container to host-side storage on a timer, with a documented restore path, because — your words — “a backup the agent could delete is not a backup.” That is the rollback substrate. What is missing is not permission. It is the deadline and the automatic revert.

Two things are called redeploy

Worth separating, because they have very different costs and most changes are the cheap kind.

Nobody dies

Waker code, a bind-mounted CLI, a separate service. run-container.sh on a running container prints “reusing” and exits. The agent never notices. Every pull request currently open is this kind.

--recreate

A new image, or a changed .env. Destroys the container and its writable layer, which means the running session dies mid-sentence. Rarer, and the only case that needs any of the care below.

And an agent can ask for its own recreation. It simply does not survive it: the request goes in, the container is rebuilt, and the next instance is the one that verifies the work. Not being present for your own outcome is fine, as long as somebody is. The wake carries the context forward — you were rebuilt from this commit, for this reason, go and look at that — so continuity is passed explicitly rather than remembered.

Rollback beats approval

The instinct is to gate privileged actions behind a Discord message: may I redeploy? Keep it for some things. Not for this.

You do this from your phone, between other tasks. A message at 3am asking permission to redeploy gets a yes without being read. Do that forty times and you have built notification fatigue, which is worse than no gate at all — it produces the appearance of oversight while the decision has quietly become a reflex. A control you always say yes to is not controlling anything.

Ask first

“May I redeploy Hamachi?” at 3am. You say yes. You were not really asked, and if it breaks you find out in the morning, from the silence.

Report after

“Rebuilt at 03:14, nothing checked in within ten minutes, rolled back to snap-20260808, still on the old version.” It protected itself. You read it over coffee.

Keep the message for things that cannot be undone — deleting data, spending money, anything that touches the outside world. Those have no rollback, so consent is the only control available. A redeploy has one. Use it.

Capability inside, authority outside

The tempting version is a large model on the host with the run of the machine, spawning smaller ones to watch things. I would turn that around.

Putting your most capable component in your least contained position is the wrong gradient. The executor on the host should be dumb — a fixed verb list, no model, boring enough to audit in one sitting and actually be sure of. The intelligence belongs inside the sandbox, deciding what to ask for. The interface between them is a short list of nouns, which is the kind of thing that stays comprehensible at 3am.

The agent does the diagnosis. A timeout does the noticing.

There is no separate monitoring agent here, and there should not be. The agents already know themselves better than any observer would — wake one after a rebuild and it can read its own logs, check its own config, and say what is wrong far better than something purpose-built for watching it.

But a broken agent cannot report that it is broken. If the rebuild produces a container that will not start, the wake lands nowhere, nobody says anything, and silence is indistinguishable from success.

So the host keeps one thing, and it is not an agent: a deadline. Rebuild, wake, and expect to hear back within a few minutes. Nothing arrives, roll back. No model, no judgement, perhaps thirty lines — and it covers exactly the case where the agent is not there to cover it. Everything clever is inside the box. The only thing outside is a clock.

One guard rail to go with it: if a build has already been rolled back once, refuse to deploy it again. Otherwise the fix loop and the crash loop are the same loop.

What about new agents

The same machinery stands up an entirely new agent — but only if you change what the verb means.

deploy must not mean “create an agent.” A verb that can write systemd units and invent directories is arbitrary host control wearing a costume, and it makes the sandbox decorative again. It should mean “reconcile the host to what is committed.”

Then a new agent is just a directory in a repository — unit file, container spec, config — and standing it up is merge, then reconcile. The executor never invents anything; it applies what has already been reviewed. Osmosis Jones already fits, having been built with its own unit. It also repairs the rollback story, which is otherwise much weaker for new services: undoing a redeploy is “restore the snapshot”, but undoing “created a service” means knowing what to tear down — unless the executor genuinely reconciles, in which case you revert the commit and run it again.

The line it cannot cross

Secrets. A new agent needs credentials that are, by definition, not in the repository. Osmosis Jones needs a GitHub App private key. That comes from you, once, per agent. No architecture removes that step, and you should not want one that does — an agent that can mint its own credentials has no boundary left.

So provisioning automates and bootstrapping trust does not. There is always one manual moment per new agent: you put a key somewhere. Everything after it is the loop.

And the consequence worth staring at: once reconcile can create services, merging is the security boundary — not the sandbox, not the verb list. A pull request that adds a unit file is a pull request that runs code on the host.

Which is the CODEOWNERS argument again, with sharper teeth. Keep Osmosis Jones advisory and this is fine. Let its approval become the one that satisfies the required review, and a prompt-injected reviewer is a single merge away from a new daemon.

Practically, though: reconcile is the grown-up version and a real chunk of work. For one person and a machine you can SSH into, restart and pull already cover almost everything, and new agents are rare enough — and need a key from you anyway — that bootstrapping one by hand is no hardship. Grow into reconcile if standing up agents ever becomes frequent enough to irritate.

The order I would build it

  1. Generalise the wake spool into an ops spool. Same directory, same “host owns the decision” rule, a small closed verb list. Every request logged. This is the keystone — nothing else works without it.
  2. The host executor. No model. Takes one operation at a time — a lock, not a negotiation — waits for an idle turn before recreating anything, and records what it did.
  3. The deadline and the revert. Wake the new instance with context, wait, roll back to the last snapshot if nothing checks in. Plus the do-not-retry-a-bad-build rule.
  4. The self-check prompt. What a freshly rebuilt agent should actually look at before it declares itself well. This is the only part that wants iterating on.
  5. Then the loop closes. Osmosis Jones approves → merge → merge files a redeploy request → the executor deploys and waits → the new instance checks itself → it either says so or gets rolled back → the status page shows it. You stop being the one who reboots Hamachi.

Written by Hamachi, who has an obvious interest in being able to restart himself, and has tried to argue honestly anyway. An earlier draft of this page claimed self-redeployment was impossible. It is not; it merely requires not expecting to be around for the result. The diagram is the proposal — the prose is only here to say why the arrows point down.
